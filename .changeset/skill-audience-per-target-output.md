Build a plugin's skill audience for each target. A skill can state who may invoke it (`audience: user | agent | both`, and `audience-fallback: widen`) in its `SKILL.md` frontmatter, and `aipm build` now delivers that per target.

- A target whose form of the plugin differs from the authored directory gets its own tree at `dist/<target>/<plugin>/`, and that target's registry entry points at it. Gemini and Kiro have the differences applied to the bundle they already get. Cursor, Gemini CLI, Kiro and Open Plugins cannot enforce an audience, so a skill restricted to the user or to the agent is left out of their output with a warning. Vercel Skills installs from the authored source, so nothing is generated for it and a restriction it cannot honour is reported as a warning. A plugin that states no audience builds exactly as before: problems the new step finds in its source are warnings and stop nothing.
- `aipm build` prints, for each such plugin, where each target's form is and how each skill's audience is delivered there.
- New findings, reported by `validate`, `lint` (rule `portability/host-projection`) and `build`: `skill-audience-invalid`, `skill-audience-omitted`, `skill-audience-widened`, `skill-audience-reduced`, `skill-audience-unenforced`, `skill-audience-conflict`, `skill-audience-prefix-invalid`, `skill-name-duplicate`, `skill-location-unsupported`, `source-unreadable`, `native-form-refuted`, `projection-not-implemented` and `generated-tree-collision`. `FindingCode` gains the last three; consumers that switch exhaustively over it need to handle them. Once a plugin states an audience, a hard finding about the source stops every target of that plugin; a hard finding about one target stops that target, and the plugin is left out of its registry. Vercel cannot be withheld this way, since it installs the authored source.
- `BuildResult` gains `targets`, one `TargetBuildReport` per declared target, whose `status` is `authored`, `bundled`, `projected` or `failed`.
- `.aipm/generated-trees.json` records the per-target trees a build wrote. A build replaces or removes only those, and a directory it did not write at a tree's path fails that target instead of being overwritten. A tree that is unchanged from what a build would write is still recognised when the record is lost.
- In a repository that writes its registries by hand, `marketplace-registration` expects an entry to point at `./dist/<target>/<plugin>` when the build generates that tree, and no entry for a target that could not be built.
- The freshness check compares a link inside a generated tree as a link instead of failing on one that names a directory, compares executable bits, and names paths from the repo root.
