# Published vs. contributor skills

A repo that publishes a plugin usually holds two kinds of skill:

- **Published skills** are for the people who install your software. They live inside a plugin
  under the plugins root (`plugins/` by default, or the `pluginsRoot` set in `aipm.repo.ts`).
- **Contributor skills** are for the people who work on the repo: how to run it locally, how to
  cut a release. They live wherever the agent host loads project-local skills, for example
  `.claude/skills/` or `.agents/skills/`.

`aipm` builds, registers and validates published skills. It does not manage contributor skills:
where they live and how they load is each host's own convention. What `aipm` does is guard the
line between the two, because not every install channel respects it.

## Install channels, and what keeps a skill out of each

| Channel                                                                                 | How it finds skills                                                                                              | What keeps a contributor skill out                                   |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Host marketplaces (Claude Code, Cursor, Codex, Open Plugins)                            | Reads the generated `marketplace.json`, then the listed plugin directories                                       | Nothing to do. Registries list only plugins under the plugins root.  |
| Single-extension hosts (Gemini CLI, Kiro)                                               | Reads the generated repo-root extension or power                                                                 | Nothing to do. The root artifact is built from one published plugin. |
| [`skills` CLI](https://github.com/vercel-labs/skills) (`npx skills add <owner>/<repo>`) | Scans the repository for `SKILL.md` files, including host folders such as `.claude/skills/`. Ignores registries. | `metadata.internal: true` in the skill's frontmatter.                |

The last row is the one that leaks. A correct registry says nothing about what the `skills` CLI
offers.

## Marking a contributor skill

Add this to the skill's frontmatter:

```yaml
---
name: release-runbook
description: Use when cutting a release of this repo.
metadata:
  internal: true
---
```

The `skills` CLI then leaves the skill out of its listing and its default install.

This hides the skill; it does not protect it. Someone who names it explicitly
(`npx skills add <owner>/<repo> --skill release-runbook`) can still install it, and the file is
readable in the repository like any other. Don't put anything in a contributor skill that you
would not publish.

## What `aipm` checks

`aipm validate` fails when a `SKILL.md` is neither inside a published plugin nor generated by the
toolkit, and is not marked internal:

```text
[.claude/skills/release-runbook/SKILL.md] unpublished-skill-installable (hard): ...
```

`aipm build` does not fail on this; enforcing the boundary is `aipm validate`'s job.

The fix is a choice only you can make. If the skill is for contributors, mark it internal. If it
is for users, move it into a published plugin. `aipm` never edits the file for you. Don't move a
contributor skill into the plugins root, or mark a user-facing skill internal, only to clear the
finding.

Three details of how that check decides:

- **It looks at every skill file in the repo**, not only the folders and depths the `skills` CLI
  searches today, and it matches `SKILL.md` in any letter case. A `SKILL.md` kept as a test
  fixture or a docs example needs the marker too. That is deliberate: the check shouldn't start
  missing files because an install channel changes where it looks.
- **Skills you installed with the `skills` CLI are exempt.** Anything in a host's dot-folder that
  your repo's `skills-lock.json` records is third-party content, and the `skills` CLI doesn't
  offer it from your repo. Don't edit those files to add the marker.
- **A symlink to a published skill is fine.** Linking a published skill into `.claude/skills/` so
  contributors get it too is treated as the same skill, not a second, unpublished one.

`aipm lint` adds three related rules:

| Rule                                      | Severity | Meaning                                                                                           |
| ----------------------------------------- | -------- | ------------------------------------------------------------------------------------------------- |
| `correctness/published-skill-internal`    | warn     | A published skill is marked internal, so `skills` CLI users won't see it.                         |
| `correctness/plugin-self-containment`     | error    | A path or markdown link in a plugin points outside the plugin's folder.                           |
| `correctness/unpublished-skill-reference` | warn     | Published content mentions a contributor skill by name. A text match, so it can be a coincidence. |

The last two exist because a plugin is installed on its own. Anything it reaches for elsewhere in
the repo, a contributor skill included, will be missing for the user.

## Checking the result as a user

Inside the repo, contributor skills load automatically and can make a published skill appear to
work when it would fail for a user. Test from an empty directory outside the repo:

1. Install the plugin there through the host's normal flow, pointing at your local checkout.
2. Try the published skills.
3. Run `npx skills add <path-to-repo> --list` and confirm it offers only what you mean to publish.
